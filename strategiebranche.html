Stratégie de branches Git

Application .NET Core + Angular · 3 équipes · itérations de 4 semaines · plusieurs livraisons en acceptation avant chaque mise en production · 1 équipe de correctifs en production

develop porte la livraison de production en cours (2027.08). Elle livre plusieurs fois en acceptation dans la branche unique release, qui est renommée production à la mise en production. Les features de la livraison suivante (2028.02) partent de develop/2028.02.

Schéma

Les branches

  • production : ce qui tourne en production.
  • release : branche unique d'acceptation. Chaque livraison d'acceptation y fusionne develop. Renommée production à la mise en production.
  • develop : livraison de production en cours.
  • develop/AAAA.MM : livraison de production suivante (ex. develop/2028.02). Ses features en partent.
  • feature : une branche par fonctionnalité, tirée de la branche develop de sa livraison.
  • bogue : une branche par correctif, tirée de production (bogue de production) ou de la release en cours (bogue d'acceptation).

Règles

  • Les features prévues pour une livraison d'acceptation sont terminées dans develop avant d'être fusionnées dans release.
  • Une feature n'est fusionnée dans sa branche develop qu'une fois terminée. Exception : au début, le contrat ou le squelette (API, DTO) peut y être fusionné si une autre équipe en dépend.
  • Les features de 2028.02 partent de develop/2028.02, jamais de develop.
  • develop/2028.02 se synchronise avec develop deux fois par semaine, jamais l'inverse.
  • Après la mise en production de 2027.08, develop/2028.02 est fusionnée dans develop puis supprimée.
  • Un bogue trouvé en acceptation se corrige dans une branche bogue tirée de la release, fusionnée dans celle-ci puis reportée vers develop.
  • Les correctifs descendent toujours : production → release → develop → develop/2028.02.
  • Changements BD : synchroniser via modifications.sql avant de communiquer avec le responsable du modèle.
