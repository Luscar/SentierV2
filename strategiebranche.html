Stratégie de branches par renommage

Application .NET Core + Angular · 3 équipes · itérations de 4 semaines · livraisons aux 6 mois · 1 équipe de correctifs en production

Principe : les branches gardent des noms de rôle stables (develop, release, production). Une livraison avance d'un rôle à l'autre par renommage. Quand la livraison suivante démarre avant la fin de la courante, elle vit dans develop/<livraison> jusqu'à ce que develop se libère.

Schéma

  1. 1Les fonctionnalités de nov2026 sont terminées : develop est renommée release et entre en acceptation.
  2. 2develop/mai2027 est renommée develop : la livraison suivante devient la livraison courante.
  3. 3nov2026 est livrée : release est renommée production et écrase l'ancienne. mai2026 ne reste accessible que par ses tags.

Les branches

production

Ce qui tourne en production. Permanente, protégée. Écrasée à chaque livraison par release.

release

Livraison en acceptation. N'existe qu'entre le renommage de develop et la mise en production. Ne reçoit que des correctifs d'acceptation.

develop

Livraison courante en développement. Les features de cette livraison y sont intégrées au moins à chaque fin d'itération.

develop/<livraison>

Livraison suivante qui démarre avant la fin de la courante. Tirée de develop et synchronisée avec elle. Devient develop au renommage.

feature/*

Une par fonctionnalité, tirée de la branche develop de sa livraison. Synchronisée deux fois par semaine, intégrée à chaque fin d'itération.

hotfix/*

Tirée de production, fusionnée dans celle-ci (nouveau tag), puis reportée vers l'aval jusqu'à la dernière branche develop.

Cycle d'une livraison

  1. Développement : la livraison vit dans develop. Ses features s'y intègrent à chaque fin d'itération.
  2. Chevauchement : si une équipe commence la livraison suivante, on crée develop/mai2027 depuis develop. Elle reçoit tout ce qui entre dans develop (synchronisation au moins deux fois par semaine), jamais l'inverse.
  3. Fin du développement : toutes les features de nov2026 sont terminées et intégrées. develop est renommée release 1, puis develop/mai2027 est renommée develop 2. Les branches feature/* de mai2027 continuent sans changement : leur parent porte simplement un nouveau nom.
  4. Acceptation : release ne reçoit que des correctifs, chacun reporté dans develop.
  5. Livraison : tag nov2026, déploiement, puis release est renommée production 3. Il n'y a plus de branche release jusqu'au prochain renommage.

Report des correctifs

  • Toujours vers l'aval : production → release (si elle existe) → develop → develop/<livraison> (si elle existe). Jamais dans l'autre sens.
  • Reporter par fusion (merge), pas par cherry-pick : chaque branche contient alors tout l'historique de celle qui la précède, ce qui rend les renommages simples (voir ci-dessous).
  • Automatiser : un job CI fusionne chaque branche dans la suivante et ouvre une PR en cas de conflit.

Renommer en pratique (Git)

Git ne renomme pas une branche distante : on déplace le nom vers le nouveau contenu, puis on supprime l'ancien nom. Si les reports se font par fusion, chaque déplacement est une avance rapide, sans force push.

  1. develop → release : git push origin origin/develop:refs/heads/release (la branche release n'existe pas à ce moment).
  2. develop/mai2027 → develop : vérifier qu'elle contient tout develop (git log origin/develop/mai2027..origin/develop est vide), puis git push origin origin/develop/mai2027:develop et git push origin --delete develop/mai2027.
  3. release → production : vérifier que tous les hotfix ont été reportés (git log origin/release..origin/production est vide), puis git push origin origin/release:production et git push origin --delete release.
  4. Si une vérification n'est pas vide, reporter d'abord la branche manquante par fusion. En dernier recours seulement : --force-with-lease, réservé au responsable des livraisons.
  5. Prévenir les équipes : chacun fait git fetch --prune et repositionne ses branches locales suivies.

Fin des fonctionnalités avant le renommage en release

  • La norme : toute fonctionnalité prévue pour la livraison est terminée, testée et intégrée dans develop avant le renommage 1. Sa branche est alors supprimée.
  • Pendant le développement, une fonctionnalité peut s'étaler sur plusieurs itérations : elle s'intègre à chaque fin d'itération derrière un feature flag désactivé.
  • La release ne sert jamais à finir du développement : elle ne reçoit que des correctifs d'acceptation.
  • Exception, fonctionnalité en retard : décision explicite avant le renommage. Soit elle reste désactivée par son flag et sa branche se rebase sur la nouvelle develop (livraison suivante), soit le renommage est reporté.

Cycle d'une itération de 4 semaines

  1. En continu : fusionner la branche develop de sa livraison dans sa feature au moins deux fois par semaine.
  2. Dernière semaine : stabiliser ce qui sera intégré ; vérifier que le flag est désactivé par défaut.
  3. Fin d'itération : PR de la feature vers sa branche develop avec tout ce qui est terminé et testé.

Dépendances entre équipes

  • Contrat d'abord : le contrat OpenAPI et les DTO sont fusionnés dans la branche develop au début de l'itération, avant l'implémentation.
  • Client généré : client Angular généré (NSwag ou openapi-generator) ; l'équipe consommatrice travaille avec des mocks.
  • Feature flags : Microsoft.FeatureManagement côté .NET, exposés par l'API et lus par un service ou une directive Angular.
  • Branch by abstraction pour remplacer de l'existant sans casser l'autre équipe.

Points chauds de conflit (.NET + Angular)

Changements BD

Synchroniser les changements BD via le fichier modifications.sql avant de communiquer avec le responsable du modèle.

Fichiers partagés

Routage Angular, package-lock.json, enregistrement DI dans Program.cs. Préférer des modules et routes en lazy loading par fonctionnalité.

Mises à jour de dépendances

Versions d'Angular ou packages NuGet : tâche dédiée, fusionnée rapidement dans develop, jamais dans une branche de fonctionnalité.

Règles d'équipe

  • Toutes les fonctionnalités d'une livraison sont terminées et intégrées dans develop avant son renommage en release.
  • Une seule release à la fois : elle doit être renommée production avant que la develop suivante soit renommée release.
  • Au plus une branche develop/<livraison> en parallèle de develop.
  • Aucune feature ne reste plus de 4 semaines sans être intégrée dans sa branche develop.
  • Correctifs reportés vers l'aval par fusion, le jour même.
  • production, release et develop sont protégées : seuls les PR et les renommages par le responsable des livraisons les modifient.
  • Nettoyage des feature flags après chaque livraison.
