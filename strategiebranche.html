Stratégie de branches par renommage

Application .NET Core + Angular · 3 équipes · itérations de 4 semaines · livraisons aux 6 mois · 1 équipe de correctifs en production

Une livraison avance par renommage : develop → release → production.

Schéma

  1. 1Les fonctionnalités de nov2026 sont terminées : develop est renommée release et entre en acceptation.
  2. 2develop/mai2027 est renommée develop : la livraison suivante devient la livraison courante.
  3. 3nov2026 est livrée : release est renommée production et écrase l'ancienne. mai2026 ne reste accessible que par ses tags.

Les branches

  • production : ce qui tourne en production.
  • release : livraison en acceptation.
  • develop : livraison courante en développement.
  • develop/<livraison> : livraison suivante, si elle démarre avant la fin de la courante.
  • feature/* : une fonctionnalité, tirée de la branche develop de sa livraison.
  • hotfix/* : correctif tiré de production.

Règles

  • Les features sont terminées dans develop avant son renommage en release.
  • Une seule release à la fois.
  • Les features s'intègrent dans leur branche develop au moins à chaque fin d'itération.
  • develop/<livraison> se synchronise avec develop deux fois par semaine.
  • Les correctifs descendent toujours : production → release → develop → develop/<livraison>.
  • Changements BD : synchroniser via modifications.sql avant de communiquer avec le responsable du modèle.
